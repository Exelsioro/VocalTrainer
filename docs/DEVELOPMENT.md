# Правила разработки Vocal Trainer

Приняты 24.10.2026. Приоритеты и критерии версий определены в [ROADMAP.md](ROADMAP.md).

## Обязательные принципы

1. Каждая выпускаемая версия собирается и проходит автоматические и применимые ручные проверки. Проверка XML/XAML и содержимого архива не заменяет компиляцию и запуск приложения.
2. Новые функции изолируются от существующих режимов. Изменения MIDI проверяются вместе с обычным тюнером и JSON-практикой; совместно используемые аудио- и временные ресурсы имеют явного владельца.
3. Аудиозапись включается только явным действием пользователя. Измерения, история, диагностика и экспорт по умолчанию не требуют сохранения голоса.
4. Старые JSON-упражнения продолжают работать либо получают документированную автоматическую миграцию. Изменения схем истории, экспорта и настроек также версионируются.
5. Измерения объяснимы: определены единицы, временная база, пороги достоверности, правила учёта тишины и пауз, версия алгоритма и основания итоговой оценки.
6. Каждое обновление сопровождается подходящими тестами, записью в changelog и проверенной PowerShell-сборкой. Регрессионный тест нужен для исправленного поведения, которое можно надёжно автоматизировать; формальные тесты оформления документации не требуются.

## Порядок работы

- Сначала воспроизвести проблему или описать ожидаемое поведение и критерий проверки.
- Выполнять изменения небольшими шагами. Разделение проектов не объединять с полной заменой алгоритма или формата хранения без необходимости.
- При изменении аудио проверять старт, остановку, повторный старт, освобождение ресурсов и ошибки устройства. При изменении времени проверять паузу, отмену, задержки и переходы режимов.
- Новую метрику сначала проверить на контрольных сигналах, затем на реальном оборудовании. Зафиксировать точность, ограничения и условия сравнения с предыдущими результатами.
- До закрытия v0.5.1 добавлять только проверки, документацию и исправления, необходимые для стабилизации текущих сценариев.

## Проверки и сборка

Полная проверка и автономный Windows-дистрибутив:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1 -SelfContained
```

Скрипт запускает тестовые проекты через `dotnet run` и обновляет `dist/Release`. В `dist` допускаются только последние `Release` и, при необходимости, `Debug` (`-Configuration Debug`). Датированные сборки, старые версии, архивы, скриншоты и логи там не сохраняются.

ZIP и специальные пакеты создаются только по явной просьбе пользователя: `build.ps1 -SelfContained -Package`, результат — в `artifacts/packages`. Проверочные файлы хранятся в `artifacts/` или `.build-tmp/`. Если EXE занят, нужно сообщить о блокировке; дополнительные папки сборок в `dist` не создаются. `-SkipTests` подходит для локальной диагностики; такой запуск не подтверждает готовность релиза.

При отдельной проверке:

```powershell
dotnet build .\VocalTrainer.sln --configuration Release
dotnet run --project .\tests\VocalTrainer.AlgorithmTests --configuration Release
dotnet run --project .\tests\VocalTrainer.WindowsTests --configuration Release
```

`dotnet test` пока не заменяет эти команды: текущие тесты — исполняемые программы с собственными проверками. Переход на xUnit возможен в v0.5.2, если сохраняется покрытие регрессий.

WPF-тест проверяет настоящее окно, привязки и отрисовку вкладок. Аппаратные сценарии проверяются отдельно по [TESTING-v0.5.1.md](TESTING-v0.5.1.md). При необходимости ограничений проверочной среды они явно указываются в отчёте; непроверенный сценарий не отмечается как успешный.

## Условия выпуска

- Выполнены критерии соответствующей версии из дорожной карты.
- Сборка и обе группы автопроверок успешны; новые предупреждения разобраны.
- Выполнены затронутые ручные сценарии, а для первого релиза — занятие 10–15 минут.
- Готовый опубликованный EXE отдельно запускается и штатно закрывается; проверены комплектные упражнения, MIDI и зависимости Runtime. Состав ZIP проверяется при явно запрошенном создании пакета.
- Изменения форматов проверены на старых примерах; при необходимости включены миграции.
- В changelog отражены изменения поведения и ограничения; обновлены инструкции и протокол проверки.
- Непройденные проверки и известные дефекты перечислены явно. Критическим считается дефект, препятствующий основному занятию, приводящий к потере данных или записи аудио без явного действия пользователя.

## Git и CI в v0.5.2

Настроить Git, определить удалённый репозиторий и публиковать релизы из зафиксированной ревизии. До этого локальная сборка не считается подтверждением воспроизводимости из чистого checkout.

Windows workflow GitHub Actions должен устанавливать SDK согласно `global.json`, восстанавливать зависимости, собирать решение, запускать обе группы тестов и обновлять Release через `build.ps1`. После публикации проверяются наличие примеров и запуск готового EXE. ZIP создаётся только при отдельном запросе пакета; логи и служебные артефакты хранятся вне `dist`.

Для WPF-проверок подтвердить работоспособность оконного окружения runner. Проверки реального микрофона не заменяются результатом облачного CI. Сетевой аудит зависимостей не отключается в настройках проекта ради успешного CI; временные ограничения окружения фиксируются отдельно.
